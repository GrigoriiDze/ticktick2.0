# Архитектура

## Из чего состоит

Один код на TypeScript и React, три сборки

| Сборка | Чем | Что даёт |
|---|---|---|
| Программа на ПК | Tauri 2, установщик .exe | Своё окно, трей, автозапуск, напоминания при закрытом окне, автообновление |
| Телефон | Capacitor, APK | Обычное приложение, точные напоминания через локальные уведомления |
| Браузер | тот же код на Firebase Hosting | Запасной вход с чужого компьютера, можно не публиковать |

Сервер и база — Firebase на бесплатном тарифе Spark: вход через Google, база Firestore, хостинг. Своего сервера нет

## Папки

```
app/                 общий код
  src/data/          единственное место, которое знает про Firestore
  src/domain/        чистая логика без Firebase и UI: повторы, даты, умные списки, сортировка
  src/ui/            экраны и компоненты
  src/platform/      различия ПК / телефона / браузера: вход, уведомления, файлы
src-tauri/           обёртка для ПК
android/             обёртка Capacitor
tools/import/        импорт из TickTick
```

UI берёт данные только через `data/`. Если когда-нибудь уйдём с Firebase, переписывается одна папка

## Модель данных

Взята со схемы десктопного TickTick (его база SQLite, снята 20.10.2026), упрощена. Всё лежит под пользователем, чужие данные недоступны по правилам безопасности

```
users/{uid}/projects/{id}   name, color, groupId, sortOrder, viewMode: list|kanban|timeline,
                            kind: task|note, closed, isInbox
                            site: { address, contactName, contactPhone, budget, drawingsUrl,
                                    stage: measure|estimate|supply|install|commissioning|done }
                            site заполнен — список считается объектом и попадает на экран «Объекты»
users/{uid}/groups/{id}     name, sortOrder, open
users/{uid}/tags/{id}       name, color, parent, sortOrder
users/{uid}/columns/{id}    projectId, name, sortOrder          (канбан)
users/{uid}/tasks/{id}
  projectId, parentId, columnId, sortOrder
  title, content, kind: text|checklist
  items: { [itemId]: { title, done, sortOrder, completedAt } }   подзадачи-пункты
  priority: 0|1|3|5          как в TickTick: нет, низкий, средний, высокий
  status: open|done|wontdo, completedAt
  start, due                 время в UTC (мс) или дата 'YYYY-MM-DD' для задач на весь день
  isAllDay, timeZone, isFloating
  repeat                     RRULE, например 'RRULE:FREQ=WEEKLY;BYDAY=MO'
  repeatFrom: due|done, exDates[]
  reminders: { [id]: 'TRIGGER:-PT15M' }
  tags[], pinnedAt
  waiting: { kind: payment|delivery|approval, until }   метка «ждём», фильтр «Зависло»
  address                    у встреч, для кнопки Яндекс Навигатора
  createdAt, updatedAt, deletedAt
```

Общие поля у всех записей: `createdAt`, `updatedAt` (время сервера), `deletedAt`

Привычки, отметки привычек и помодоро добавим, если клиент ими пользуется. Их схема в TickTick тоже снята: HabitModel, HabitCheckInModel, PomodoroModel

## Синхронизация

Firestore хранит полную копию данных на устройстве (постоянный кэш в IndexedDB), держит соединение с сервером и сам досылает правки, сделанные без сети. Наша задача — не испортить ему жизнь. Правила:

- **ID записи создаёт устройство** (`doc()` без запроса к серверу), иначе офлайн-создание ломается
- **Пишем только изменённые поля** (`updateDoc` с путём поля), задачу целиком не перезаписываем. Если на телефоне поменять дату, а на ПК название, сохранятся обе правки. Перезапишется только одно и то же поле, изменённое на двух устройствах, и победит последняя правка
- **Пункты чек-листа, напоминания — словарь по id, не массив.** Массив в Firestore перезаписывается целиком, и правки двух устройств затрут друг друга
- **Удаление мягкое**: `deletedAt` + корзина. Окончательно чистим через 30 дней
- **Порядок (sortOrder) — дробные числа** между соседями, чтобы перетаскивание меняло одну запись, а не весь список
- Время правки ставит сервер (`serverTimestamp()`), часам телефона не доверяем

## Даты и повторы

- Задача со временем хранится в UTC + часовой пояс, задача на весь день — строкой даты без пояса, иначе при перелёте она уедет на другой день
- Повторы считает библиотека `rrule`. У повторяющейся задачи при отметке создаётся выполненная копия, а у самой задачи сдвигается дата (так делает TickTick)
- Вся логика дат лежит в `domain/` и покрыта тестами

## Напоминания

Каждое устройство само ставит себе уведомления по своей локальной копии и пересчитывает их при каждом изменении задач

- Телефон: `@capacitor/local-notifications`, точные будильники Android
- ПК: процесс в трее Tauri + плагин уведомлений, автозапуск с Windows

## Вход

Google не пускает к своему входу из встроенных окон приложений

- Телефон: нативный плагин `@capacitor-firebase/authentication`
- ПК: вход через системный браузер с возвратом в программу
- Браузер: обычное окно входа Firebase

## Безопасность

- Правила Firestore: читать и писать можно только `users/{uid}/**`, где `uid` — свой
- В коде нет секретов. Конфиг Firebase для клиентских приложений публичный по замыслу, защиту дают правила и вход
- Проверка App Check, чтобы с базой работали только наши сборки

## Бэкап

Автоматический экспорт Firestore в Google Cloud на бесплатном тарифе недоступен. Вместо него программа на ПК раз в день сохраняет все данные в JSON-файл в папку пользователя и хранит последние 30 копий. В настройках есть ручной экспорт и импорт этого файла

## Импорт из TickTick

1. CSV-выгрузка из настроек TickTick: задачи, списки, теги, даты, повторы, подзадачи
2. Официальный API TickTick (OAuth): проекты и задачи, кнопкой из приложения
3. База десктопного TickTick (`AppData\Roaming\Tick_Tick\TickTick.db`): всё, включая привычки и помодоро

Импорт пишет пачками до 500 операций и не создаёт дублей при повторном запуске: id из TickTick сохраняется в поле `sourceId`

## Проверки

- Vitest для `domain/`: повторы, даты, умные списки
- Эмулятор Firebase для синхронизации: два клиента, правки офлайн, конфликт одного поля, конфликт разных полей, удаление против правки
- Playwright для основных путей в браузерной сборке
